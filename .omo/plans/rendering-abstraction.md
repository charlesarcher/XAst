## TL;DR (For humans)

Replace direct X11/Xlib rendering calls — **434 X11 call sites across 16 files** (pinned census, §Verification Strategy; this is the single count used by this plan) — with an abstract `RenderingEngine` interface (27 methods — 21 core + 6 seams: `pollEvents`, `setScissorRect`, the render-target trio, `getPresentTransform`, plus the v6/S1 menu-adapter pair `createTextureFromRGBA32`/`drawTriangles` counted in CORE; every core method takes LOGICAL CLIENT coordinates and is backend-transformed uniformly — v6.1/D17.4g), then implement X11 (pass-through, pixel-identical), OpenGL 4.5 Core, and — behind the USER GATE — a Vulkan 1.x backend via GLFW. **X11 + GL constitute the minimum visible surface; Phase 4 (Vulkan) is self-contained and excisable** — deleting it must leave a complete, passing plan. X11 keeps GXor compositing, X fonts, its original draw emission order, and its per-event input model verbatim; the GL/VK backends map the same semantics onto GPU primitives with a fixed canonical draw order (GL/VK-only contract — never applied to X11, O5-M4). The game loop restructures into per-object `Step()`/`Render()` split with explicit `beginFrame()`/`endFrame()` and an explicit `setScissorRect()` (the HUD draws outside the play-area scissor). Input is per-event end-to-end (`pollEvents` seam; GLFW_REPEAT dropped). Deterministic QA is built as a Phase-1 prerequisite (seeded RNG, pre-refactor baseline capture, headless harness) so every pixel-identity gate is machine-checked under a tiered identity regime — byte-exact on X11-vs-X11; masked-region identity plus seeded state-hash parity for cross-backend comparisons (XOR-overlap, vector-rasterized and thick-line regions are NOT pixel-comparable across rasterizers — F2/O5-C1) — and a numeric lane guards the intersector/gravity FP paths this repo exists to stress. Menus ship working on EVERY backend — Motif/Xt Options dialog verbatim on X11; Dear ImGui on GL/VK behind a thin domain-owned seam (D9). The window is freely user-resizable on ALL backends while the logical play-area resolution NEVER changes: uniform-scale centered letterbox (aspect preserved, never stretched) keeps physics/logic determinism intact (D17.4). Build system: the existing `makefile` extended with a `BACKEND` variable — no CMake. **48 executable tasks across 6 phases.**

## Design Decisions

### D1: Backends first-class — X11 + GL minimum visible surface, Vulkan gated
**Decision:** X11, GL and (gated) Vulkan backends implement one `RenderingEngine` interface with identical game-rendering feature parity. **X11 + GL are the minimum visible surface of this plan.** The Vulkan phase ships only after the USER GATE is confirmed; it is written self-contained and excisable (no task before Phase 4 depends on Vulkan content; deleting Phase 4 leaves a complete passing plan). "Identical" parity means **game-rendering** visual parity; menus are functional on EVERY backend (Motif/Xt on X11, Dear ImGui on GL/VK — D9) but are backend-specific BY DESIGN and excluded from cross-backend identity gates (Q10/Q11 scope GAMEPLAY frames only).
**Rationale:** Round-4 receipt section H: the Vulkan scope call is an owner decision that was never taken — v4 must not resolve it, only gate it. All five reviewers endorsed the three-backend-behind-one-interface shape.
**Impact:** Phases 0-3 + 5 are Vulkan-agnostic; every Vulkan-specific defect (finite acquire timeout, OUT_OF_DATE/SUBOPTIMAL path, layer/loader availability checks, identity QA by harness byte-diff) is fixed inside Phase 4. GL-side defects are fixed regardless of the gate.

### D2: Hybrid rotation strategy
**Decision:** GPU rotation via the MVP matrix (`setTransform`) for wireframe-only objects. Texture-mapped compositing for bitmap-decorated objects. Pre-computed textures for pure-bitmap objects. The `RotatorDisplayData` hierarchy has 5 subclasses:
- `NonRotVectorData` / `RotVectorData`: wireframe (or wireframe + bitmap interior) → GPU rotation for outline, texture lookup for interior
- `MaskedRotVectorData`: wireframe + interior + clip mask (all rock types) → GPU rotation + texture composite + clip-mask texture
- `RotPixmapData` / `MaskedRotPixmapData`: pure bitmap (thrust flames) → pre-computed textures (no rotation benefit)
**Degenerate case (m13):** non-rotating objects (`NonRotVectorData`) take the **static-texture path** — the texture is drawn with the identity transform; no `setTransform` call is issued and no angle is interpolated. This is the fast path for all non-rotating decorations and must be exercised by the numeric/visual QA lane (GL rotation task, Phase 3).
**Rationale:** Eliminates pre-computed wireframe pixmaps for rotating objects on GL/VK; retains pre-computed textures where rotation offers no visual change.
**Impact:** On GL/VK, wireframe rotation is uniform-buffer driven; on X11 the pre-computed pixmap pipeline is unchanged (D14).

### D3: GXor is load-bearing — RETAIN on X11; GXor accumulation is order-invariant among GXor-family draws only
**Decision:** `GXor` at `playingField.H:135` provides implicit transparency and MUST be retained on the X11 backend. `rotatorDisplayData.C:193` fills object pixmaps with a black background (`XFillRectangle` with `background=BlackPixel`); GXor makes black source pixels transparent (0 XOR dest = dest) while colored pixels paint (color XOR 0 = color). Without GXor, black source pixels would erase previously drawn overlapping objects.
**Order-invariance (U25 ruling, R4-M16):** `XSetFunction` appears **exactly once** repo-wide (`playingField.H:135`, GXor). Per-pixel XOR against fixed source pixels is **associative and commutative**, therefore the X11 composite image is **independent of object draw order** — no Z-order contract exists or is needed on X11. GL/VK alpha blending is **non-commutative**, so D8 fixes ONE canonical draw order for the GPU backends. The GXcopy + clip-mask paths (`rockGroup.H:184-197`, `explosionGraphic.H:103-117`) are a masking-correctness concern, not a draw-order concern.
**Impact:** GXor moves into X11Backend as an internal GC (not exposed in the API). GL/VK approximate the visual result via alpha blending against the play-area framebuffer in the D8 canonical order; X11 keeps its existing draw sequence verbatim. **Stated plainly (O5-C1): XOR accumulation over overlapping colored pixels is NOT bitwise reproducible by alpha blending** — wherever two objects' pixels coincide on screen (explosions over ships/rocks), the GL/VK frame legitimately differs pixel-wise from X11. Such overlap regions are excluded from cross-backend pixel gates and covered by state-parity checks instead (F2 tiered regime).

### D4: Frame timing — preserve dynamic pacing
**Decision:** Preserve the existing `uSecondsPerFrame` + diffTime compensation mechanism. Default 62500 µs (16 fps) per `playingField.H:98`. Pacing at `playingField.H:504-505`: `if (diffTime<uSecondsPerFrame) usleep(uSecondsPerFrame-diffTime)`. User-configurable at runtime via the Options FPS scale widget (`options.H:729`; callback → `AlterFramesPerSecond` at `options.H:3086-3088` → `playingField.H:672` `uSecondsPerFrame=newUSecondsPerFrame`). On GL/VK the same timing loop runs with `glfwSwapInterval(0)` (compositors may override — documented escape clause, m10: frame-period QA accepts VSync-capped rates and records the measured rate, it does not fail the build on compositor behavior).
**FPS configurability (S1/D9-v6):** user frame-rate configuration exists on EVERY backend — X11 keeps the Motif widget verbatim; GL/VK get an equivalent Dear ImGui slider (task 44) writing the same `uSecondsPerFrame` value (`playingField.H:672`) through the domain-owned `OptionsMenu` seam (`options.H` itself stays an X11-only compile path).
**Risk:** Driver/compositor VSync override of `glfwSwapInterval(0)`. Documented as a known limitation; the pacing mechanism itself is identical across backends.

### D5: RenderingEngine API — one interface, corrected method set
**Decision:** One abstract class, three backend classes. The v3 20-method set is **corrected to **21 core methods + 6 seam methods (27 total; v6/S1 added `createTextureFromRGBA32(const uint8_t* pixels, int w, int h)` — Dear ImGui font-atlas upload — and `drawTriangles(const float* verts, int count, TextureId tex)` — per-vertex-color indexed triangles, the menu draw-batch primitive — to CORE; v6.1 adds the seam `getPresentTransform(float& outScale, int& outOffsetX, int& outOffsetY)` so the adapter converts logical↔window with zero platform types; core methods take LOGICAL CLIENT coordinates and are backend-transformed uniformly, `drawTriangles` being the sole window-space method)****: `createTextureFromXBM` is **DELETED** — XBM files route through the backend-agnostic decode utility (Phase 2 task) into `createTextureFromBitmap`; `pollEvents` (typed events only — GLFW_REPEAT dropped at the boundary, B3) and `setScissorRect` (explicit; `beginFrame` does NOT own the scissor, R4-M3) are added; the render-target trio (`createRenderTarget`/`beginRenderTo`/`endRenderTo`) implements the **render-to-texture decision** for the Button off-screen faces (FBO on GL/VK; X11 keeps off-screen Pixmap — decision encoded, M1/R4-M6 closed). `TextureId = uint64_t` (not `void*`, m20). `getFontMetrics` exposes per-font **max_bounds** (ascent/descent/width — used by Stage layout `stage.H:145-146` and Button size computation `button.H:173-174`, D12). `clear()` is specified against the **background GC** (GXcopy, black foreground — the dual-GC design, R4-M1). `initWindow` returns a success/failure boolean (M12/U21 reconciled; full signature in D15).
**Rationale:** R4 §I.7 — the v3 API lacked the seams T12 (render target), D8 (scissor), and B3 (events) actually need, and `void*` TextureId was a type-safety gap.
**Impact:** Full corrected C++ sketch in the §RenderingEngine API section. Every v3 method that survived keeps its name; behavioral contracts (scissor ownership, clear GC, event typing) are restated there.

### D6: Clip masking — pre-computed mask textures on GL/VK
**Decision:** Upload existing 1-bit clip masks as single-channel (R8) GL/VK textures; the fragment shader `discard`s on mask-off pixels. X11 keeps its native clip-mask GCs unchanged. Clip masks are pre-computed bitmaps: `explosionEdge_bits`/`explosionMiddle_bits`/`explosionCenter_bits` (`explosionGraphic.H:94-100`) and polygon-derived rock masks (`rotatorDisplayData.C`). Stencil state would add a render pass for no benefit.
**Impact:** One extra texture per masked draw. Negligible cost. Mask geometry (the 3 `XSetClipMask`/`XSetClipOrigin` sites in `explosionGraphic.H` and the rock sites in `rockGroup.H:184-197`) is absorbed into the `drawTextureMasked` engine call on X11 (clip origin passed internally).

### D7: Screen-wrap — single draw + scissor clip, with explicit coordinate mapping
**Decision:** Single draw at the wrapped box position + scissor/viewport clip to the play area. No double-draw. `Box::WrapMovingBox` (`box.H:251-288`) teleports **only when the box is fully off the opposite edge**; while an object **straddles** the edge, no wrap occurs — the original draws it once, clipped at the pixmap boundary. Double-draw would paint a ghost at the opposite edge during straddle — an artifact the original does not have.
**Coordinate mapping (m3):** The X11 pixmap is oversized (`playArea.Width()+4*ROCK::scale` × `playArea.Height()+4*ROCK::scale`, `playingField.H:131`). The scissor rectangle is expressed in **LOGICAL CLIENT coordinates** = `(playAreaX, playAreaY, playArea.Width(), playArea.Height())`, where `playAreaX/playAreaY` are the Stage layout values (`stage.H:176-177`) — v6.1 binding rule (D17.4g): core methods take logical coords and the backend applies the present transform uniformly. The API has **no implicit play-area concept**: the domain (Stage) computes the rect each frame and calls `engine->setScissorRect(...)` explicitly. HUD elements (score/title/shipyard/button — `stage.H:168-171`, `:161-162`, `:172-175`, `:163`) draw with the scissor **disabled** (see D8).
**Impact:** Wrapping behavior is byte-identical on X11 (the X11 backend's window blit already clips via blit geometry at `stage.H:258/:269`) and correct on GL/VK (explicit scissor in LOGICAL CLIENT coords, backend-transformed, y-offset included — v6.1 coordinate-space rule).

### D8: Game loop restructure — split, bracket, ordered, un-scissored HUD
**Decision:** Restructure to frame-based rendering.
- **Current flow:** `MissScript()` per object → `XCopyArea` (inside `Intersect()`); `stage.DrawPlayingField()` → `XCopyArea` (pixmap → window); `XFillRectangle` clear for the next frame.
- **New flow:** (1) update all objects — per-object `Step()` (position/physics only, **no drawing**); (2) `engine->beginFrame()`; (3) `engine->clear()` (background GC, GXcopy black — the X11 clears at `playingField.H:202/:312/:638`); (4) `engine->setScissorRect(play area)`; (5) draw world objects — GL/VK in the **canonical order below**, X11 in its original per-object emission order (verbatim, O5-M4); (6) `engine->setScissorRect(nullptr)`; (7) draw HUD (score/title/shipyard/button); (8) `engine->endFrame()` (X11: XSync + pixmap blit; GL/VK: swap/present).
- **Canonical draw order (GL/VK contract ONLY — binding there, NEVER applied on X11):** rocks → player ship → thrust flames → enemies → enemy bullets → ship bullets → explosions → HUD. X11 keeps its existing draw sequence **verbatim** — task 24 must not emit the canonical order on X11 (O5-M4: D3's invariance covers only GXor-family accumulation; the GXcopy+clip-mask writes are order-dependent relative to overlapped GXor content, so a reordered X11 emission is not provably byte-identical and is not attempted — Q13 guards the original order instead). On GL/VK the order is binding: alpha blending is non-commutative, and Q10/Q11 compare against these very frames.
- **Scissor ownership:** `beginFrame` does **NOT** set or own the scissor. `setScissorRect` is called explicitly by the domain: play-area rect for the world pass, **null** for the HUD pass. This fixes v3's frame-1 hollow shell (R4-M3/m14) where the whole HUD — all of it outside the 640×512 play rect — was clipped by a scissor `beginFrame` owned.
**Rationale:** v3's absorbed-scissor `beginFrame` clipped the HUD; the draw order was unspecified while GL/VK blending requires one.
**Impact:** The update/render split is where float-order drift enters the T20-class of bugs — the numeric lane (Phase 5) pins the intersector paths so reordering cannot corrupt them silently.

### D9: Menus on EVERY backend — Motif/Xt verbatim on X11, Dear ImGui behind a thin seam on GL/VK (v6/S1 — REVERSES the grayed-out ruling at the USER's direction)
**Decision:** Menus are functional on EVERY shipped backend. The two implementations stay SEPARATE fat impls behind ONE thin domain-owned seam — **no unified widget toolkit** (Out of Scope):
- **The seam (domain-owned, engine-typed only):** `OptionsMenu` — `open()/close()/isOpen() const/tick()/handleGameEvent(const GameEvent&)/renderOverlay(RenderingEngine&)`. The domain constructs exactly one instance per backend selection in `main()` (the task-13 pattern); `RunGame` calls `tick()`, feeds every polled `GameEvent` through `handleGameEvent(...)`, and calls `renderOverlay(engine)` at the fixed loop points below. Zero widget-library symbols may appear in domain files (F1 unchanged).
- **X11 leg (`MotifOptionsMenu`):** wraps the existing Motif/Xt dialog VERBATIM — it is the **second X11 event island**: a hand-rolled modal pump at `options.H:2542-2571` (an `XtAppNextEvent` switch over stage-window events, `XPutBackEvent` at `:2560` for `WM_DELETE_WINDOW`, `XtDispatchEvent` at `:2568` for the rest). **Stated plainly: `XtAppMainLoop`/`XtAppInitialize` do NOT exist in this repository** (grep-verified; the coupling is not an owned Xt main loop). Coupling is via **referenced globals** — `stage.window` (`:2543`), `stage.autoRepeatState` (`:2547`, grep-verified single site; its paired `XAutoRepeatOn`/`XAutoRepeatOff` calls sit at `:2548`/`:2550` — R6-M1 cite correction), `stage.Refresh()` (`:2554`, corrected from :2556 — M5-N4), `playingField.WM_DELETE_WINDOW` (`:2559/:2560`) — with **zero `extern` declarations** in `options.H`. The 6 unguarded Options sites (`playingField.H:69` declaration `Boolean RunGame(Options&)`; `:300` definition; `:457` & `:616` `options.RealizeWindow()`; `:565` function-local construction — **`Options` is a function-local, NOT a global**; `:591` the `RunGame(options)` call) are `#ifdef`-guarded as planned; on GL/VK the guarded contract becomes `Boolean RunGame(RenderingEngine&, OptionsMenu&)` (task 2's Phase-0 wording updated accordingly). `nativeHandle()` remains the X11-consumer seam (the Motif impl needs `{Display*, Window}`). `MotifOptionsMenu` is implemented INSIDE `options.H` under the backend guard (R6: deliberately NO new Motif-bearing file — this keeps the F1 exception zone a closed set and the 229-site census exact); at close/re-arm it performs ONE backend present-transform refresh (geometry query) so a resize made while the modal was open cannot leave a stale dest-rect (R6 staleness fix).
- **GL/VK leg (`ImGuiOptionsMenu`):** Dear ImGui driven through a **RenderingEngine-only adapter** — font atlas uploaded once via `createTextureFromRGBA32`; draw lists batched via `drawTriangles` (per-vertex color) with per-command clipping through `setScissorRect` (each ImDrawCmd WINDOW-space clip rect is inverse-mapped to LOGICAL client coords first — v6.1 coordinate-space rule); **zero glad/vulkan symbols outside `glBackend`/`vkBackend`** (grep gate). The overlay draws AFTER the letterboxed game frame in WINDOW space (D17.4(e)). Input mapping: `ImGuiIO` is fed from the SAME `pollEvents(GameEvent*)` stream (KeyDown/KeyUp/MouseDown/MouseUp/MouseMove/CursorEnter/CursorLeave → AddKeyEvent/AddMouseButton/AddMousePos equivalents; since `GameEvent` x/y are LOGICAL client coords but ImGui needs WINDOW-space, the adapter reads `getPresentTransform` (v6.1) every frame to set `io.DisplaySize = canonical*scale + 2*offset` and to forward-map `MousePos` before feeding it — R6, else menu hit-testing breaks at any non-canonical size) — the GLFW_REPEAT drop (D16) is SAFE because the menu has no text fields (sliders/toggles/buttons only; stated so no repeat-delivery regression can hide). The FPS slider writes the same `uSecondsPerFrame` path (D4); volume/mute and preferences save/load get ImGui equivalents (task 44 scope list).
- **dear_imgui vendoring:** like glad/stb — pinned upstream SHA + MIT license file recorded in `vendor/PINNED.md`, checksummed at fetch, offline-first, plain `-I` integration, no submodule/CMake machinery (O5-N2 regime). Lands at task 30 (GL leg) so task 31's first GL link already compiles it; VK needs nothing extra (the adapter is engine-only).
**Stated consequences (v6):** none of the old deprivations remain — frame-rate configuration (D4), volume/mute, and preferences save/load exist on EVERY backend. The README grayed-out note is DELETED (replaced by the S1 feature documentation); the README xpra-scaling block is marked LEGACY/SUPERSEDED by native resizing (S2, task 44).
**Impact:** The pump stays exactly where it is on X11 (inside the X11-only region; F5's scripted open/apply/close unchanged). On GL/VK there is still NO second event pump: the menu is NON-modal — it consumes events fed by the SAME `RunGame` drain (no nested loop), and opening it pauses simulation (one stated semantic, mirrored on X11 by the existing modal pause). Options frame-clock re-arm (`startTime = ResumePlay()` after close — see D16) now applies on ALL backends (GL/VK re-arm when the ImGui menu closes). Identity gates (Q10/Q11) scope GAMEPLAY frames only — menu screens are backend-specific BY DESIGN.

### D10: Build system — makefile only; ONE task owns the transition
**Decision:** Extend the existing `makefile` (`CXX=g++`; `CXXFLAGS=-I/usr/include/X11 -O3 -w` at makefile:2 currently has **zero `-D` flags**) with a `BACKEND=X11|GL|VK` variable. **ONE task (Phase 0 task 1) owns the makefile transition foundation:**
1. `BACKEND` variable with **all three targets existing from Phase 0**, each with a per-backend **objects compile-only target** (`obj/X11/...`, `obj/GL/...`, `obj/VK/...` — per-backend object dirs or suffixes so `BACKEND` switches never relink stale or mixed objects; N5/R4-M8).
2. `-std=c++17` for all targets (strstream is removed in **C++17** — the v3 "C++26" framing is wrong and is not repeated anywhere in this plan; the sstream migration in task 5 compiles under it).
3. `-w` **replaced** with targeted warning flags (e.g. `-Wall -Wextra -Wno-unused-parameter`).
4. `CXXFLAGS += -DX11_BACKEND` for the **X11 target only** — the macro is defined **nowhere** today (makefile:2 zero `-D` flags; 0 source occurrences). This task is a **precondition for every header-guard acceptance** (B1); with the guards in and the macro undefined, the X11 target would compile with all X11 includes stripped and fail.
5. The `objects` compile-only target lets Phase 0 prove guarded sources compile **without** X11/Motif headers, without the engine existing yet — no link step, no backend code required.
**The GL/VK LINK rules** (`XAsteroids-GL`: `+ -lglfw -lGL`, no `-lXm -lXt -lX11`; `XAsteroids-VK`: `+ -lglfw -lvulkan`, no `-lXm -lXt -lX11`) **land in Phase 3** (task 29) when the GL backend exists — the VK link rule lands inside Phase 4 (task 37). This replaces v3's incoherent T9-before-T24 sequencing (U23): targets exist before flags drop, and nothing links a flag for code that doesn't exist yet. `compositePixmap.C` + `rotatorDisplayData.C` are **not** "unchanged-and-linked-into-every-target": their X11 pipelines sit inside `#ifdef X11_BACKEND` with engine-based `#else` branches (D14), compiled for every target.
**Rationale:** A 22-line makefile; per-backend link flags are proportional. CMake is a full rewrite and is rejected (v3 decision, retained).
**Impact:** `make BACKEND=X11` keeps `-lXm -lXt -lX11`; `make BACKEND=GL` links without Motif/Xt/X11; the stale XBM dependency list on the `XAsteroids.o` rule (makefile:15 — stale vs the default build; noted, refreshed in task 29) is fixed there. The `AutoRepeatOn` utility target (standalone, 3 X11 calls, `AutoRepeatOn.C`) remains an X11-only build artifact.

### D11: Engine lifecycle + dependency injection — one ctor per class, `RenderingEngine&`
**Decision:** `main()` creates the backend FIRST, calls `initWindow`, then constructs the 11 globals by pointer with the engine injected **by reference**. Each migrated class gets **ONE constructor taking `RenderingEngine&`**. **v3's `#ifdef X11_BACKEND` dual-ctor approach is REJECTED** (it bakes a transitional hack into the design); there is **no `extern RenderingEngine*` global** and no global pointer at all. The 11 globals at `XAsteroids.C:13-30` (`stage` :13, `button` :14-17, `score` :18, `explosionGraphic` :19, `shipGroup` :20, `shipYard` :21-25, `shipBulletGroup` :26, `rockGroup` :27, `enemyGroup` :28, `enemyBulletGroup` :29, `playingField` :30) become the injection point; Phase 0 task 6 moves them from static-initialization values to pointer construction in `main()` with the *current* X11 signatures, and Phase 1 task 13 changes the constructors to the single `RenderingEngine&` form.

  - `'e'` (left rotation) / `'r'` (right rotation): KeyPress sets `AngularVelocity` **and** a pending-rotation flag; **KeyRelease consumes the pending flag and zeroes angular velocity** (`playingField.H:362-381` / `:408-445`) — release-time semantics a boolean key-state array **cannot express**.

**Impact:** No per-frame key polling anywhere in this plan; the leaky event boundary (XEventsQueued/XLookupString/XRefreshKeyboardMapping/XPutBackEvent, m5/m8) closes because the whole island moves into the backend. `XRefreshKeyboardMapping` is a no-op equivalent on GL/VK (physical-key mapping is static for the session — documented).
